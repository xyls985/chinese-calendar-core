# 算法、时间基准与精度

## 计算规则

1. 输入按固定 UTC+08:00 解释，不读取系统时区，不应用夏令时或真太阳时。
2. 年柱以计算得到的立春瞬时为界；月柱以十二个“节”的瞬时为界。
3. 日柱在公历零点变化，六十日循环采用 2024-01-01 甲子日为参考。
4. 时柱使用五鼠遁；23:00–23:59 为当日晚子时，沿用当日日干。
5. 农历月初一取合朔在 UTC+08:00 所在的公历日；冬至所在月定为十一月。
6. 相邻冬至之间有十三个月时，首个不含中气的月为闰月；农历年以正月初一变化。

十二个换月“节”为立春、惊蛰、清明、立夏、芒种、小暑、立秋、白露、寒露、立冬、大雪、小寒。“中气”用于置闰，不直接作为四柱换月边界。

## 天文计算

- 太阳黄经采用截断的 VSOP87D 地球黄经项，加上近似光行差与主要章动项，再数值求解目标黄经。
- 合朔采用 Meeus 风格的月相周期公式和摄动修正，目前只保留了部分附加周期项。
- 动力学时与世界时之间的 ΔT 使用分段多项式估计，按公历年份取值。
- 儒略日用于内部时间换算；角度差归一化到 `[-180, 180)`。

这些实现优先考虑简洁、无外部依赖和四语言可移植性，**不属于完整高精度星历实现**。

## 已知精度限制

对独立历算实现比较的 1813–2100 年 6,912 次节气中，最大时刻差约 101.42 秒，中位差约 21.70 秒。对中央气象署 2026–2027 年初的 28 次节气，12 个显示分钟相差 1 分钟。官方表格本身只列到分钟，这些数值不构成严格的秒级误差上界或对所有年份的保证。

交节附近的分钟输入可能得到不同的年柱、月柱。例如：

| 输入（UTC+08:00） | 当前结果的年柱、月柱 | 官方公布分钟及辅助高精度结果 |
|---|---|---|
| 2026-02-04 04:02 | 乙巳 己丑 | 气象署立春为 04:02；sxtwl 为 04:01:51，已进入丙午 庚寅 |
| 2026-07-07 09:57 | 丙午 甲午 | 气象署小暑为 09:57；sxtwl 为 09:56:39，已进入丙午 乙未 |

当前保留上述近似行为，未用单日硬编码来掩盖误差。升级太阳黄经、章动、光行差或 ΔT 模型时，应重跑独立精度比较和四语言回归。需要在交节附近严格判断四柱的应用，应采用精度满足要求的星历方案。

节气显示时刻经过四舍五入，但换柱使用内部未取整时刻。因此“显示为 04:02”不代表内部瞬时一定早于或等于 04:02:00。

## 历史历法

输入允许 1813–2100 年，**允许计算不等于保证与当年历史历书一致**。1929 年以前的历法使用过不同的北京地方时间、太阳时和历算方法。固定 UTC+08:00 的现代重算可能与当时颁行的农历日期相差一天。

香港天文台历表核对中，1914、1916、1920 年各有连续 30 天农历差异。例如 1916 年新月约在 2 月 3 日 16:05 UT，换成固定 UTC+08:00 为 2 月 4 日 00:05；历史历表春节是 2 月 3 日。这是规则兼容性问题，不能通过给所有新月统一减一天来解决。

现代日期核对范围及远期预测说明见 [VALIDATION.md](VALIDATION.md)。

## 缓存与并发

Python 和 JavaScript 缓存已求得的节气及农历月份。Python 缓存不通过公共接口暴露；并发首次计算可能重复工作。Java 使用 `ConcurrentHashMap` 安全发布结果；C++ 使用线程局部 Map，避免共享写入。缓存仅是性能优化，不影响公共结果类型。
